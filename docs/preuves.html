Explorer une architecture IA sur Azure

Mon point de départ était la curiosité : comment relier un modèle IA à une API, organiser son traitement et exécuter l’ensemble sur Azure ? J’ai pris une réunion administrative fictive comme cas pratique. L’application en tire des propositions de décisions et d’actions, que l’utilisateur peut ensuite approuver ou rejeter.

J’ai construit ce cas pratique avec assistance IA pour découvrir l’environnement Azure et comprendre comment ses services peuvent accueillir une application IA. Le choix d’une petite réunion fictive laisse de la place pour explorer l’architecture, sans dépendre de données réelles.

Du texte à une décision humaine

FastAPI reçoit la demande et lance le graphe LangGraph. Le modèle Azure OpenAI sélectionne des identifiants de passages dans la transcription. Le service accepte uniquement ces références et assemble les citations depuis le texte source.

Une échéance absente reste vide. Le graphe s’arrête ensuite à une étape de revue et reprend lorsque l’utilisateur approuve ou rejette le brouillon. Cette séparation entre génération et décision est au cœur du fonctionnement de l’application.

            ↓
Pause → approbation ou rejet humain

Identité, données et ressources temporaires

L’identité managée du conteneur lui donne accès à la seule ressource Azure OpenAI prévue pour l’essai. Aucune clé de modèle n’est intégrée au code public.

La ressource était située en Suisse Nord. Le déploiement Global Standard permet un traitement du modèle hors de cette région ; la localisation de la ressource ne garantit donc pas un traitement exclusivement suisse. Toutes les données de l’essai étaient fictives.

Les ressources Azure temporaires ont été supprimées après l’essai. Le portfolio reste un site GitHub Pages qui présente ce travail ; il ne lance aucun appel au modèle.

Explorer le projet à son tour

Le dépôt rassemble le code FastAPI et LangGraph, les tests, le Dockerfile, le manifeste Kubernetes, le modèle Bicep et le guide d’exécution. Le mode déterministe permet de commencer localement sans compte de modèle ni service Azure.

python -m pip install -r requirements-test.txt
python -m unittest discover -s tests -v
python -m uvicorn pv_demo.api:app --host 127.0.0.1 --port 8000

Dans un second terminal, la commande python scripts/smoke.py parcourt les routes HTTP jusqu’à l’approbation du brouillon.
