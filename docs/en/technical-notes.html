This decision log prototype lets you examine the full workflow, from a transcript to human approval. I built it with AI assistance to make my technical choices, source code and tests available for review.

This personal project uses an entirely fictional administrative meeting. Its code, sample data and tests let you reproduce the scenario from start to finish.

Open the GitHub repository ↗

A workflow with a human review step

The FastAPI service receives the request and runs a LangGraph graph. In Azure OpenAI mode, the model selects passage identifiers from the transcript. The service checks those references and reconstructs the quotations from the source text.

If no deadline is given, the deadline field stays empty. Processing then pauses for a person to approve or reject the draft. The graph resumes only after that explicit decision.

Identity, data and test duration

The Azure test used a managed identity for the container and an inference role scoped solely to the Azure OpenAI resource. No model API key is embedded in the public code.

The resource was located in Switzerland North. The Global Standard deployment type allows model processing outside that region, so this test does not establish that processing took place exclusively in Switzerland. It used fictional data only.

The Azure test resources were deleted after verification. The portfolio presents the architecture and verification results; it does not make any model calls.

Reproduce the scenario

The repository contains the FastAPI and LangGraph code, tests, Dockerfile, Kubernetes manifest, Bicep template and setup guide. Deterministic mode lets you get started without a model provider account or an Azure service.

python -m pip install -r requirements-test.txt
python -m unittest discover -s tests -v
python -m uvicorn pv_demo.api:app --host 127.0.0.1 --port 8000

In a second terminal, python scripts/smoke.py verifies the HTTP workflow. The repository guide describes the prerequisites, Docker and Kubernetes steps, and optional Azure model configuration.

The service keeps its state in memory in a single instance. It is a reproducible prototype; sustained use would require suitable persistence and access controls tailored to the deployment context, among other changes.
