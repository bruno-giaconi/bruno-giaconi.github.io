PERSONAL PROJECT · AI & workflow

Exploring an AI architecture on Azure

I wanted to explore Azure by building a small project from end to end. I chose a decision log based on a fictional transcript to explore how an API, an AI workflow, a container and cloud services fit together.

What is the application for?

Curiosity was my starting point: how do you connect an AI model to an API, organise its workflow and run the whole system on Azure? I used a fictional administrative meeting as a practical example. The application produces proposed decisions and actions that the user can then approve or reject.

The user journey

  1. 01

    Start with a simple scenario

    The fictional transcript is divided into identified passages. This small dataset keeps the focus on the architecture and the path information takes through it.

  2. 02

    Connect the API to the workflow

    A FastAPI request starts the LangGraph graph. Deterministic mode supports local development; Azure OpenAI mode uses the model to prepare the draft.

  3. 03

    Structure the model response

    Structured output contains passage identifiers. The service accepts only identifiers from the transcript and retrieves their quotations, leaving the deadline empty when no date is given.

  4. 04

    Make room for a human decision

    The graph pauses processing at the review step. A separate action approves or rejects the draft; a second decision on the same draft is rejected.

  5. 05

    Move from application to container

    Docker packages the service and its dependencies. GitHub Actions runs the eleven tests, builds the image and exercises the HTTP workflow in an ephemeral Kubernetes kind cluster.

  6. 06

    Explore execution on Azure

    The image is then used in Azure Container Instances. A managed identity gives the container access to the Azure OpenAI resource without embedding a model API key in the code.

What makes it useful

Orchestration with LangGraph

Preparation, waiting and resumption become explicit workflow states.

The interaction between model and application

Structured JSON gives the service a precise contract, while quotations and dates remain tied to the transcript.

The user’s role

Generation prepares a draft. Approval or rejection remains a user action, built into the API workflow.

Runtime environments

The same service moves from local development to Docker, then to kind and Azure Container Instances. Bicep provides a further path towards AKS, explored only as far as template compilation.

Azure managed identity

Access to the model relies on the container’s identity and a role scoped to the relevant inference resource.

Current scope

A personal project using fictional data, with state held in memory in a single instance. The Azure resources used on 9 November 2026 were deleted after the experiment. The portfolio presents this exploration and does not call the model. AKS was not deployed; sustained use would require suitable persistence and access controls, among other changes.

My contribution

I designed and developed this personal project with AI assistance, exploring FastAPI, LangGraph, Azure OpenAI, containerisation and managed identity. The meeting scenario provides a practical thread for understanding each component and its role in the architecture.

What I built

  • A FastAPI service and a LangGraph graph prepare a draft, then wait for a person to approve or reject it.
  • Azure OpenAI produces structured output: the model selects passages, and the service assembles quotations from the transcript.
  • Deadlines come from the source text; when no date is given, the field remains empty.
  • A GitHub Actions pipeline combines eleven automated tests, a Docker build and an HTTP workflow on Kubernetes kind.
  • The same image was run in Azure Container Instances, with no public IP address, a managed identity and GPT-4.1 mini inference.

What the project offers

Explore the choices that connect an AI application to its runtime environment: orchestration, structured exchanges, human involvement, identity and deployment. A project for learning by building and gaining a better understanding of this ecosystem.
