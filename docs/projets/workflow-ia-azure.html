PROJET PERSONNEL · IA & workflow

Explorer une architecture IA sur Azure

J’avais envie de découvrir Azure en construisant un petit projet de bout en bout. J’ai choisi un relevé de décisions à partir d’une transcription fictive pour explorer les liens entre une API, un workflow IA, un conteneur et les services cloud.

À quoi sert l’application ?

Mon point de départ était la curiosité : comment relier un modèle IA à une API, organiser son traitement et exécuter l’ensemble sur Azure ? J’ai pris une réunion administrative fictive comme cas pratique. L’application en tire des propositions de décisions et d’actions, que l’utilisateur peut ensuite approuver ou rejeter.

Le parcours utilisateur

  1. 01

    Partir d’un scénario simple

    La transcription fictive est découpée en passages identifiés. Ce petit jeu de données permet de se concentrer sur l’architecture et sur le chemin suivi par l’information.

  2. 02

    Relier l’API au workflow

    Une requête FastAPI lance le graphe LangGraph. Le mode déterministe permet de travailler localement ; le mode Azure OpenAI utilise le modèle pour préparer le brouillon.

  3. 03

    Organiser la réponse du modèle

    La sortie structurée contient des identifiants de passages. Le service accepte uniquement ceux de la transcription et en reprend les citations, avec une échéance vide si aucune date n’est donnée.

  4. 04

    Donner une place à la décision humaine

    Le graphe suspend le traitement à l’étape de revue. Une action distincte approuve ou rejette le brouillon ; une deuxième décision sur le même brouillon est refusée.

  5. 05

    Passer de l’application au conteneur

    Docker regroupe le service et ses dépendances. GitHub Actions exécute les onze tests, construit l’image et lance le parcours HTTP dans un cluster Kubernetes kind éphémère.

  6. 06

    Explorer l’exécution sur Azure

    L’image est ensuite utilisée dans Azure Container Instances. Une identité managée donne au conteneur l’accès à la ressource Azure OpenAI, sans intégrer de clé de modèle dans le code.

Ce qui fait la différence

L’orchestration avec LangGraph

Les étapes de préparation, d’attente et de reprise deviennent des états explicites du traitement.

Le dialogue entre modèle et application

Le JSON structuré donne au service un contrat précis, tandis que les citations et les dates restent rattachées à la transcription.

Le rôle de l’utilisateur

La génération prépare un brouillon. L’approbation ou le rejet reste une action de l’utilisateur, intégrée au fonctionnement de l’API.

Les environnements d’exécution

Le même service passe du poste local à Docker, puis à kind et Azure Container Instances. Bicep ouvre une étape supplémentaire vers AKS, restée au stade de la compilation.

L’identité managée Azure

L’accès au modèle repose sur l’identité du conteneur et un rôle limité à la ressource d’inférence concernée.

Périmètre actuel

Projet personnel sur des données fictives, avec un état conservé en mémoire dans une seule instance. Les ressources Azure utilisées le 9 novembre 2026 ont été supprimées après l’essai. Le portfolio présente cette exploration et n’appelle pas le modèle. AKS n’a pas été déployé ; une utilisation durable demanderait notamment une persistance et une gestion des accès adaptées.

Ma contribution

J’ai conçu et développé ce projet personnel avec assistance IA, en explorant FastAPI, LangGraph, Azure OpenAI, la conteneurisation et l’identité managée. Le scénario de réunion sert de fil conducteur pour comprendre chaque composant et son rôle dans l’ensemble.

Ce que j’ai construit

  • Une API FastAPI et un graphe LangGraph pour préparer un brouillon, puis attendre son approbation ou son rejet par une personne.
  • Azure OpenAI produit une sortie structurée : le modèle sélectionne des passages, et le service assemble les citations à partir de la transcription.
  • Les échéances proviennent du texte source ; lorsqu’aucune date n’est indiquée, le champ reste vide.
  • Un pipeline GitHub Actions réunit onze tests automatisés, la construction Docker et un parcours HTTP sur Kubernetes kind.
  • La même image a été exécutée dans Azure Container Instances, sans IP publique, avec une identité managée et une inférence GPT-4.1 mini.

Ce que le projet apporte

Explorer les choix qui relient une application IA à son environnement d’exécution : orchestration, échanges structurés, intervention humaine, identité et déploiement. Un projet pour apprendre en construisant et mieux comprendre cet écosystème.
